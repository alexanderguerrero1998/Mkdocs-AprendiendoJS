JAVASCRIPT CAP21

LONG POLLING

Es una app de charlas en tiempo real (como un foro en vivo), donde el problema es:

¿Cómo hace el servidor para avisar a todos los navegadores cuando algo cambia?

El problema: El servidor no puede iniciar una conexión hacia el navegador, solo el navegador puede conectarse al servidor. El servidor no sabe quién tiene la página abierta.

La solución: Long Polling

En lugar de que el servidor avise, el navegador pregunta constantemente pero de forma inteligente.

Como ya mencionamos anteriormente el problema principal es que el servidor no puede iniciar una conexión hacia el navegador, y los routers suelen bloquear ese tipo de conexiones de todos modos. Entonces la solución es que sea el navegador quien mantenga una conexión abierta hacia el servidor. Sin embargo, HTTP normal no sirve para esto porque funciona en un solo sentido: el cliente pregunta, el servidor responde una vez y se cierra la conexión. Existe WebSockets que permite comunicación bidireccional, pero es más complejo de implementar. Por eso se usa una técnica más simple llamada long polling, que funciona así:

  • El navegador hace una solicitud HTTP y se queda esperando la respuesta.
  • El servidor no responde hasta que haya algo nuevo que informar.
  • Cuando llega una novedad, el servidor responde y el navegador abre inmediatamente una nueva solicitud.
  • Si pasa demasiado tiempo sin novedades, el servidor responde vacío para evitar que la conexión expire, y el navegador vuelve a preguntar.

Esto significa que el servidor puede tener miles de conexiones abiertas al mismo tiempo, una por cada usuario que tenga la página abierta. Aquí es donde Node.js brilla, ya que su modelo asíncrono le permite manejar todas esas conexiones simultáneas sin necesidad de crear un hilo separado para cada una, algo que otros servidores tradicionales no harían tan eficientemente.

INTERFAZ HTTP

Contexto general El texto forma parte del diseño de una aplicación web colaborativa para gestionar charlas (tipo conferencia o meetup). Antes de construir el servidor o el cliente, el autor propone pensar primero en la interfaz HTTP que los conectará, siguiendo buenas prácticas en el uso de métodos y cabeceras HTTP, y usando JSON como formato de intercambio de datos.

Estructura de rutas Todo gira en torno a la ruta /talks. Las rutas que no empiecen con /talks servirán archivos estáticos como el HTML y JavaScript del cliente. Esto es una separación clara entre la API y los recursos front-end.

Operaciones disponibles (CRUD)

  • GET /talks — Devuelve la lista completa de charlas, cada una con título, presentador, resumen y sus comentarios.
  • PUT /talks/{título} — Crea o reemplaza una charla. El cuerpo debe incluir presenter y summary en JSON.
  • GET /talks/{título} — Recupera una charla individual en formato JSON.
  • DELETE /talks/{título} — Elimina una charla específica.
  • POST /talks/{título}/comments— Agrega un comentario a una charla, enviando author y message.

Como los títulos pueden contener espacios u otros caracteres especiales, deben codificarse con encodeURIComponent al construir la URL, por ejemplo Cómo%20hacer%20el%20caballito.

Encuestas prolongadas (Long Polling) Esta es una de las partes más interesantes del diseño. El problema a resolver es: ¿cómo sabe el cliente cuándo hay cambios en la lista de charlas sin estar preguntando constantemente al servidor? La solución usa dos mecanismos HTTP que normalmente se asocian al caché:

ETag: el servidor incluye este header en sus respuestas con un número de versión que representa el estado actual de la lista. Cada vez que algo cambia, ese número se incrementa. If-None-Match: el cliente, en su próxima solicitud, envía el ETag que recibió antes. Si nada cambió, normalmente el servidor respondería con un 304 Not Modified de forma inmediata.

Sin embargo, aquí se introduce una variación importante: en lugar de responder de inmediato con 304, el servidor retiene la respuesta y espera hasta que la lista cambie o hasta que pase un tiempo máximo. Para indicar esta intención, el cliente incluye el header Prefer: wait=90, que le dice al servidor que está dispuesto a esperar hasta 90 segundos. Solo cuando hay algo nuevo, el servidor responde con 200 OK y los datos actualizados, incluyendo el nuevo ETag. Esto reduce enormemente la cantidad de solicitudes innecesarias, a diferencia del polling tradicional donde el cliente pregunta repetidamente en intervalos fijos.

EL SERVIDOR

Comencemos construyendo la parte del programa del lado del servidor. El código en esta sección se ejecuta en Node.js.

ENRUTAMIENTO

El servidor se construye usando createServer de Node.js para iniciar un servidor HTTP. El desafío principal es que, al recibir una solicitud, el servidor necesita distinguir entre los distintos tipos de peticiones según su método HTTP (GET, PUT, POST, DELETE) y su ruta (/talks, /talks/{título}, etc.).

El problema con las cadenas de if

Una solución básica sería usar una larga cadena de declaraciones if para evaluar cada combinación de método y ruta. Sin embargo, esto rápidamente se vuelve difícil de leer y mantener a medida que crece el número de rutas. El autor reconoce que existe una manera más elegante de resolverlo.

¿Qué es un enrutador?

Un enrutador es un componente cuya responsabilidad es recibir una solicitud entrante y dirigirla hacia la función específica que sabe cómo manejarla. En lugar de anidar condiciones, el enrutador permite registrar manejadores asociando un método HTTP y un patrón de ruta (expresión regular) con una función. Cuando llega una solicitud, el enrutador la compara contra los patrones registrados y ejecuta el manejador correspondiente. Por ejemplo, se le puede indicar al enrutador que las solicitudes PUT cuya ruta coincida con /^\/talks\/([^\/]+)$/ deben ser atendidas por una función específica. Esa expresión regular representa /talks/ seguido de un título de charla (cualquier texto que no contenga otra barra /).

Extracción de parámetros

Una funcionalidad importante del enrutador es que no solo identifica qué manejador usar, sino que también extrae las partes relevantes de la ruta. Esto se logra mediante los grupos de captura de las expresiones regulares, es decir, las partes entre paréntesis. En el ejemplo anterior, el título de la charla quedaría capturado y se pasaría directamente como argumento a la función manejadora, evitando que cada función tenga que parsear la URL por su cuenta.

Implementación propia vs. paquetes externos

Aunque existen varios paquetes de enrutadores bien probados disponibles en NPM, el autor decide escribir uno desde cero con el propósito de ilustrar el principio detrás de su funcionamiento. Esto es coherente con el enfoque pedagógico del texto: entender cómo funciona algo internamente antes de delegar esa responsabilidad a una librería externa.

export class Router {

    constructor(){
        this.rutas = [];
    }

    add(metodo, ruta, manejador){
        this.rutas.push({metodo,ruta,manejador});
    }
    async resolver(solicitud, contexto) {
       let {pathname} = new URL(solicitud.url,"http://d")

       for(let {metodo,ruta,manejador} of this.rutas ) {
        let match = ruta.exec(pathname);
        if(!match || solicitud.metodo != metodo) continue
        let partes = match.slice(1).map(decodeURIComponent);
        return manejador(contexto, ...partes, solicitud)
       }

    }

}

¿Qué es y qué exporta el módulo?

El módulo exporta una clase llamada Router. A partir de ella se crea un objeto enrutador que tiene dos responsabilidades principales: registrar manejadores y resolver solicitudes.

Método add

Permite registrar manejadores asociando:

  • Un método HTTP (GET, PUT, POST, DELETE)
  • Un patrón de URL (expresión regular)
  • Una función manejadora

Método resolver

Cuando llega una solicitud, resolve busca entre los manejadores registrados cuál coincide con el método y la URL de esa solicitud, y ejecuta su función manejadora devolviendo su resultado.

El argumento context

Las funciones manejadoras reciben un valor context que se les pasa desde resolver. Esto es importante porque así los manejadores pueden acceder al estado del servidor sin necesidad de variables globales.

Parámetros que recibe el manejador

Cada manejador recibe tres cosas:

  • El context (estado del servidor)
  • Las cadenas capturadas por los grupos () de la expresión regular, ya decodificadas con decodeURIComponent para convertir caracteres como %20 en espacios normales
  • El objeto solicitud completo

SIRVIENDO ARCHIVOS

Cuando una solicitud no coincide con ninguna ruta del enrutador, se asume que es una petición de un archivo estático del directorio public.

En lugar de construir un servidor de archivos propio, se usa el paquete de NPM serve-static, que es más robusto y soporta funciones avanzadas como caché, algo que una implementación propia del capítulo anterior no tenía.

¿Cómo funciona serve-static ?

Se llama con un directorio raíz y devuelve una función manejadora que acepta tres argumentos:

  • request
  • response
  • Una función next que se ejecuta si ningún archivo coincide

El orden de prioridad es importante: el servidor primero revisa si la solicitud corresponde a una ruta especial del enrutador, y solo si no coincide con ninguna, la pasa a serve-static para buscar un archivo. Por eso se envuelve en otra función, para controlar ese orden.

El servidor maneja dos tipos de solicitudes:

Solicitudes de la API → manejadas por el enrutador.

Son las rutas con lógica especial relacionadas a /talks:

  • GET /talks → obtener lista de charlas
  • PUT /talks/titulo → crear una charla
  • DELETE /talks/titulo → eliminar una charla
  • POST /talks/titulo/comments → agregar un comentario

Estas se registran manualmente en el enrutador usando el método add, asociando un método HTTP, una expresión regular y una función manejadora.

Solicitudes de archivos estáticos → manejadas por serve-static

Son las peticiones de archivos físicos guardados en la carpeta public como index.html, app.js, styles.css, etc. No se registran en el enrutador porque sería imposible registrar cada archivo uno por uno. En cambio, serve-static las maneja automáticamente buscando el archivo en la carpeta public. 

import { error } from "node:console";
import {Router} from "./router.js"

const router = new Router();
const defaultHeaders =  {"Content-Type": "text/plain"};

export async function serveFromRouter(servidor,solicitud, respuesta, next) {

    let resuleto = await router.resolver(solicitud,servidor)
    .catch(error=>{
        if (error.status != null) return error;
        return {body: String(error), status: 500};
    })
    if(!resuleto) return next()
    let {body, status = 200, headers = defaultHeaders } = await resuleto;

    response.writeHead(status, headers);
    respuesta.end()

}

serveFromRouter tiene la misma interfaz que fileServer, recibiendo (request, response, next). Esto permite encadenar manejadores donde cada uno puede manejar la solicitud o pasarla al siguiente llamando a next(). El flujo es:

  • serveFromRouter → intenta resolver la solicitud con el enrutador
  • fileServer → si no coincidió, busca un archivo estático
  • notFound → si tampoco encontró nada, responde con 404

¿Cómo funciona internamente serveFromRouter?

Llama a router.resolve() que devuelve una promesa. Hay tres posibles resultados:

  • Error controlado (con error.status) → se devuelve el error tal cual
  • Error inesperado → se responde con 500
  • null (ninguna ruta coincidió) → se llama a next() para pasar al siguiente manejador

Si sí hay resultado, se extraen body, status (por defecto 200) y headers (por defecto text/plain), y se envía la respuesta.

CHARLAS COMO RECURSOS

Almacenamiento de charlas

Las charlas se almacenan en la propiedad talks del servidor, un objeto donde cada propiedad es el título de la charla. Se registran manejadores en el enrutador para exponerlas como recursos HTTP bajo/charlas/[título].

GET de una charla

Busca el título en server.talks:

  • Si existe → devuelve los datos en JSON con status 200
  • Si no existe → devuelve un error 404 con un mensaje

DELETE de una charla

Si existe → la elimina con delete y llama a server.updated() En ambos casos devuelve status 204 (sin contenido)

Vale la pena notar que el 204 se devuelve siempre, independientemente de si la charla existía o no.
